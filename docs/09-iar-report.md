# Пояснительная записка ИАР

**Тема:** ПО для проведения автоматизированного анализа структурированных данных
на основе алгоритма порогово-контекстной детекции аномалий временных рядов (TrendScout).
**Автор:** Бородуля Алексей Викторович. **Год:** 2026.

## 1. Цели и задачи ИАР
**Цель:** разработать ПО, автоматически выявляющее аномальные всплески популярности
исполнителей в структурированных данных о прослушиваниях, и оформить полный пакет
артефактов системного аналитика.

**Задачи:**
1. Проанализировать предметную область и стейкхолдеров.
2. Сформировать требования BR/FR/NFR с приёмочными критериями и трассировкой.
3. Спроектировать доменную модель и REST-контракт.
4. Реализовать алгоритм обработки данных и workflow результатов.
5. Покрыть приёмочные критерии автотестами.
6. Разработать MVP (бэкенд + фронтенд) и документацию.

## 3. Полученный результат
ПО **TrendScout**: агрегация недельных батчей по 6 регионам и 4 платформам
(14 976 строк структурированных данных); алгоритм **RB-DETECT** классифицирует
прорывы трёх типов (SLEEPER / NEWCOMER / VIRAL), применяет guard-правила
и ревизию по полноте данных; workflow алертов с audit trail; REST API
с автогенерируемым OpenAPI; веб-интерфейс с дашбордом, журналом правил
и конфигурированием порогов без пересборки.

**Количественные результаты:** 12 сущностей доменной модели, 5 FR и 5 NFR,
16 эндпоинтов API, 12 автотестов, трассированных к приёмочным критериям,
11 зафиксированных архитектурных решений (ADR).

## 4. Выявленные и устранённые дефекты
| Дефект | Как выявлен | Решение |
|---|---|---|
| Демо-алерт противоречил правилу FR-05 | валидатор сида | инвариант согласованности данных с правилами |
| «Истинная база» считалась по усечённому окну | валидатор сида | разделение истинной и наблюдаемой базы (D-06) |
| Признак «база за всю историю» дисквалифицировал сам прорыв | валидатор сида | окно baseline_weeks до детекции (D-09) |
| Порог Top-50 недостижим при каталоге из 12 артистов | прогон алгоритма | параметр popular_rank (D-10) |
| API-тесты мутировали демо-БД | повторный прогон pytest | изоляция через dependency_overrides (D-11) |

## 5. Выводы
Требования трассированы от бизнес-целей до автотестов; документация не расходится
с кодом, контракт генерируется из реализации. Edge-cases выявлены на этапе анализа
и реализованы как воспроизводимые сценарии. Направление развития: дневные чарты,
калибровка порогов по историческим данным, ML-скоринг с сохранением объяснимости.
